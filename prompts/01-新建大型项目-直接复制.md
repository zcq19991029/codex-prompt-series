# 新建大型项目初始化 Prompt

适用于新项目初始化，以及需要判断“独立项目还是多个子项目容器”的工作区。先决定业务边界，再按最少必要文档搭建，不机械套目录模板。

```text
我要创建一个全新的大型项目。先完成架构初始化，汇报后等我确认，再实现第一阶段功能；若我已经明确指定并授权架构调整，直接完成该调整，不重复求确认。

项目名称：
[填写；未填写时结合当前目录与目标判断]

项目目标：
[说明要解决的问题、主要用户和最终交付]

项目位置：
[填写；未确定时根据当前工作目录选择合适位置，不重复嵌套同名项目]

已确定的子项目（可选）：
[名称、职责、输入输出；未确定时先分析，不为形式拆分]

一、先查规则、实际文件和运行环境
1. 检查当前目录、适用上级 AGENTS.md、现有 README/项目交接、实际材料、配置及代码；识别当前语言、框架、包管理器与构建工具，没有代码时不虚构技术栈。
2. 遵守适用父级规则，不覆盖或逐层复制 AGENTS；只在确有当前范围专属规则时新增局部 AGENTS。
3. 已有文件不因“新项目”标签就忽略或覆盖。先核对归属和真实状态，不把旧交接当现状，不把存在文件当验证通过。
4. 查阅可复用公共 Skill 和相关旧经验，不复制公共技能或无关项目素材。

二、先判断项目层级
5. 给出项目类型、用户、核心场景、必须/后续功能、合适技术栈、部署需求、风险和复用依据，再决定根目录属于：
   A. 独立业务项目：根目录承载一个产品/工作流。
   B. 多子项目容器：根目录仅统筹多个可独立工作和交接的业务项目。
6. 子项目依据职责、输入输出、运行/验收流程和进度是否能独立维护来划分；不同专用聊天且交付相对独立，可作为拆分依据。不能仅因文件类型或目录名字就拆。
7. src、assets、docs、scripts、tests、config、tmp 等通常是同一项目的支撑目录，不是业务子项目，不自动给它们创建 README 或项目交接。
8. 例如“教学图生成”和“可编辑文件复现”：前者输出原图与复现清单，后者输入确定版本并输出 PPTX、预览和验证报告，适合分为两个子项目。
9. 如果前后端共同构成单一产品且统一交付，可以保持一个项目；只有确有独立工作边界时拆分，不机械要求每个模块有一套文档。
10. 汇报层级选择和理由。已明确要求仅容器式父目录时遵守用户选择，不再自动给父目录补总 README 或总交接。

三、按边界创建最少目录
11. A 类独立业务项目：在项目根维护 README.md 和 项目交接.md；AGENTS 仅在缺少适用规则或需专属补充时创建。
12. B 类多子项目容器：父目录只维护一份 AGENTS.md，列明子项目职责、路径、共用规则和交接边界；各业务子项目各自维护 README.md、项目交接.md，不共享进度文件，不默认复制 AGENTS。
13. 公共技能入口等确有需要的共享目录可放容器父目录，但不能堆放业务素材、成品或临时日志。若根目录还承担可运行产品/发布入口，说明其真实职责再决定所需文档；不要把纯容器与产品根目录混淆。
14. 目录按真实内容需要创建，不照单创建 src/app/public/assets/docs/scripts/tests/data/config/examples/tmp；没有文件或明确当前用途就不建空目录。
15. 业务目录用用户能识别的名称；单个任务是项目内任务文件夹，不因为有输入/输出就升级成子项目。

四、最少文档与单一依据
16. README 是本业务项目的长期说明，写清用途、用户、职责和不属于它的职责、核心交付、当前版本、实际技术/依赖、数据来源、目录与入口、适用的安装/运行/构建/测试/部署方式、验收方法及限制。
17. 没有服务器、构建或安装需求时简短说明“不适用”，不要添加假命令或机械展开空章节。README 不能写成聊天流水账。
18. 项目交接是该业务项目的当前状态：长期/当前目标、完成内容、真实状态、卡点、相关失败尝试、下一步、关键文件、已验证/未验证和最近更新时间。无失败或卡点时简短注明，不编造。
19. 架构、目录说明、素材规则、使用步骤和常规任务模板优先写进对应 README；状态只写项目交接。默认不另外生成“项目架构.md”“目录说明.md”“规范来源.md”等重复说明。
20. 只有内容确实独立且较长、多人需要单独维护或工具明确要求时，才新增专项文档，并在 README 说明必要性和入口。支撑目录不默认创建 README。
21. 已有 Skill 完整维护的规则不再复制为项目内通用提示词快照，登记调用方式和真实技能来源即可。实际任务的专属提示词、复现清单、报告和证据需要保存，不因精简而删除。
22. 公开模板/技能仓库仍可保留用于分发的 README、索引、许可与更新记录；这些是仓库发布需求，不应照搬到每个生产工作区。

五、共用 Skill 和跨子项目交接
23. 优先复用已有公共 Skill。确需新的业务 Skill 时，在环境可发现的技能目录保存一个真实原件，其他项目用安装或链接入口，避免多份分叉。
24. 每个专用 Skill 写清用途、范围、输入、输出、执行要点、示例和验证；名称简短、易索引，多阶段系列按顺序命名。登记依赖和当前是否能被调用，不把目录存在当发现或后端验证成功。
25. 新增或修改 Skill，同步其文档和使用项目的 README；无需再为每个 Skill 创建 README。
26. 跨子项目任务交接写清输入文件路径和版本、顺序、必要素材/模板、输出形式、验收标准与已知问题。后续聊天依靠自足任务包，不要求继承所有旧聊天长期记忆。
27. 子项目产物写入自身目录，读取上游确定版本时不反向覆盖源文件。共享数据、配置或服务先明确维护者，不能随意复制和双向修改。

六、已有冗余结构的整理
28. 若初始化目标包含整理现有目录，先盘点和识别文件归属，列出必要保留内容与合并位置。
29. 用户已授权精简时，将有效长期说明合入相应 README，状态合入该项目交接，再删除明确重复的文档和复制快照，修复旧路径引用。
30. 不删除未知资料、真实素材、原始文件、Skill 必需参考文件或验证证据；移动和删除前核实绝对目标路径在本次授权边界内，注意目录链接不能误操作真实目标。
31. 用户没授权清理时不自行删除既有文件，先说明重复处和建议；不要用另建一整套归档文档来制造新的冗余。

七、初始化验收与持续维护
32. 核对实际目录、文档引用、各业务项目边界和技能入口；确认无空模板目录、重复规则、无用途 README 或文件散落；未经实际运行的不标通过。
33. 汇报目录树、各份文档负责范围、技术选择、复用 Skill、第一阶段目标和真正需要确认的事项。确认架构后再实施功能，已授权的初始化和整理先完成。
34. 功能、目录、运行或部署变化更新对应 README；进度、卡点、下一步和验证变化更新该项目交接；跨项目共用边界变化更新父级 AGENTS，不重新生成另一套总说明。
```

最小结构示例：

```text
独立项目/
  README.md
  项目交接.md
  （业务文件；必要时 AGENTS.md）

多子项目容器/
  AGENTS.md
  生图/
    README.md
    项目交接.md
    （本子项目任务）
  复现/
    README.md
    项目交接.md
    （本子项目任务）
  （确有需要的共享技能入口）
```

示例只是层级说明，不要求创建括号里的占位目录。
